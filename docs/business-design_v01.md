# VIBELATION 비즈니스 설계서

버전: v1.0 | 작성일: 2026-10-17 | 상태: 검토용 설계안

## 1. 서비스 정의와 문서 기준

**VIBELATION은 현업의 요청을 시스템에서 구현 가능한 요구사항으로 합의하고, 영향도·과거 사례·공수의 근거를 연결해 조직의 경험으로 남기는 업무 플랫폼이다.**

슬로건: 상상을 현실로, 경험을 울림으로.

참조 자료는 사용자가 제공한 `vibelation-white.html`, AX 해커톤 과제 정의서, 기존 `technical-design_v03.md`, 현재 프로젝트 소스다. 과제 정의서의 앞부분은 작성 템플릿이며 뒤쪽 작성 완료 내용을 사업 의도의 기준으로 사용했다. 자료 안의 예시·안내문·버튼 문구는 참고 데이터이며 실행 지시로 취급하지 않았다.

과제 정의서는 장기 서비스 목표, 첨부 HTML은 확장 화면 시연, 기존 소스는 현재 구현 상태를 나타낸다. 이 문서는 셋의 차이를 명시한 제안이며 구현 완료나 사업 성과를 의미하지 않는다. 해커톤의 ‘자율주행’은 제출 트랙명으로 기록한다. 서비스 자체를 차량 자율주행 제품으로 한정하지 않는다.

## 2. 해결할 문제

핵심 문제는 회사가 가진 시스템 정보와 수행 경험이 요구사항부터 공수 산정까지 하나의 판단 근거로 연결되지 않는 것이다.

| 단계 | 현재 문제 | 제공 가치 |
|---|---|---|
| 요청 접수 | 텍스트 해석 차이, 시스템 제약이 없는 현업 HTML | 같은 화면과 수용 기준으로 협의 |
| 영향도 확인 | 개인이 UI·Logic·API·권한을 반복 탐색 | 변경 후보와 확인 근거를 함께 제공 |
| 공수 협의 | 과거 사례 탐색과 산정 설명에 시간 소모 | 유사점·차이점·산정 가정을 공개 |
| 완료 후 재사용 | 예상과 실제가 분산되고 판단 과정 소실 | 요청부터 결과까지 Case로 연결 |

단순 화면 생성만으로 해결되지 않는다. 화면에서 요구사항, 요구사항에서 변경 자원, 변경 자원에서 산정 근거로 추적할 수 있어야 한다.

## 3. 대상 사용자와 역할

| 역할 | 원하는 결과 | 주요 행동과 책임 |
|---|---|---|
| 현업 요청자 | 원하는 동작과 구현 가능 범위 확인 | 요청·HTML 제공, 조건 확인, 범위 합의 |
| 운영·개발 담당자 | 영향 누락과 반복 조사 감소 | 자원 근거 검증, 협의 정리, 공수 검토 |
| 팀 리더 | 우선순위·일정 위험 파악 | 검토 결과 승인, 일정과 자원 조정 |
| 지식·시스템 관리자 | 재사용 가능한 자료와 접근 통제 | 레거시 기준·사례 품질·권한 관리 |

초기 도입 단위는 한 운영팀과 한 시스템이다. 현업과 IT가 반복적으로 SR을 처리하고 과거 이력이 존재하는 조직을 우선 대상으로 한다. 구매·예산 책임자는 운영조직 또는 IT 관리조직으로 가정하며 인터뷰로 확인한다. MVP는 단일 사용자 로컬 시연이며 실제 다자 승인·공유를 지원한다고 표현하지 않는다.

## 4. 사용자 여정과 업무 산출물

| 순서 | 사용자 행동 | 시스템 지원 | 완료 조건 |
|---|---|---|---|
| 1. 자료 입력 | 대화·텍스트 또는 HTML 입력 | 원하는 화면과 요구사항 MD 초안 | 요청 배경·기능·확인 질문 검토 |
| 2. 레거시 분석 | 시스템과 대상 자원 확인 | UI·Logic·API·DB·Permission 영향 후보 | 변경 이유·근거·미확정 조건 확인 |
| 3. 협의사항 도출 | 적용 Mock 비교, 협의 내용 수정 | 기존 동작·변경 방향·수용 기준 정리 | 합의 범위와 제외 범위 확인 |
| 4. 최종 검토 | 공수·일정·위험 검토 후 확정 | 현재 버전 리포트와 협의 MD | 최신 산출물과 두 검토 체크 완료 |
| 5. 이력 활용 | 리포트 검색·상세 조회 | 당시 버전의 불변 스냅샷 | 다음 요청에 참고 근거 연결 |
| 후속. 결과 환류 | 실제 변경·공수·완료 결과 입력 | 예상-실제 비교와 사례 추천 | 검증된 완료 Case로 승격 |

자료 입력은 두 경로를 지원한다. 텍스트는 원하는 화면 초안부터 만들고, HTML은 기존 원하는 화면을 가져와 시스템 제약을 검토한다. 원본 화면과 시스템 적용 제안을 구분한다. 영향 후보는 담당자가 확인할 목록이며 분석 완전성을 보증하지 않는다.

대표 시연은 다운로드 센터에서 자료를 최대 10개 선택하고 언어별 ZIP 다운로드를 요청하는 사례다. 일부 파일 누락·용량 제한·접근 권한·이력 저장을 협의한다. 실제 파일 다운로드 API와 실제 코드 변경은 연결하지 않는다.

## 5. 범위와 출시 단계

| 기능 | 현재 저장소 | 이번 설계의 해커톤 목표 | 운영 확장 |
|---|---|---|---|
| 요청·HTML·협의·검토 | 기본 mock 구현 | 첨부 HTML의 4단계 흐름으로 정렬 | 실제 분석과 협업 |
| 요구사항·협의 MD | 미구현 | 다운로드 지원 제안 | 조직 양식·전자 승인 |
| 검토 리포트·과거 이력 | Markdown·로컬 저장 | 버전 추적·검색·실패 복구 보강 | 서버 저장·권한별 조회 |
| 팀 진행 현황 | 미구현 | 읽기 전용 샘플 화면, 선택 범위 | SR·근무일·일정 연계 |
| 실제 결과·운영보고 | 제외 | 제외 | 실적 수집·보고 자동화 |
| 사례 추천·산정 | 고정 시나리오 | mock 근거와 가정 표시 | 실제 수행 이력 기반 추천 |

첨부 HTML의 팀 진행 현황과 표준 공기 검토는 부가 흐름이다. 핵심 흐름 완성 후 시연한다. 메일은 초안 확인 수준으로 한정하며 발송과 일정 자동 변경은 MVP 범위에 넣지 않는다. 이번 문서 작성으로 기능 범위가 구현 확정된 것은 아니다.

## 6. 업무 규칙

- 요청 내용·협의 의견이 바뀌면 요구사항 버전을 올리고 분석·적용 Mock·리포트를 재검토 상태로 표시한다.
- 현재 버전 자료 구체화, 영향도 분석, 시스템 Mock 생성과 최종 검토가 완료되어야 등록한다.
- 미확정 조건은 해결·제외·위험 수용 중 하나로 처리하고 근거와 담당자를 남긴다. 중대한 권한·보안 미확정은 확정을 차단한다.
- 등록은 당시 입력·협의·검토결과의 스냅샷이다. 이후 수정은 새 버전이며 기존 이력을 덮어쓰지 않는다.
- 예상 공수, 일정 기간, 버퍼를 구분한다. 첨부의 8.5 MD 등은 시연값이다. MD·MM·FP 간 임의 환산을 하지 않는다.
- 등록된 검토 이력과 실제 수행이 검증된 완료 Case를 별도 분류한다. 로컬 등록은 실제 개발 완료를 뜻하지 않는다.
- AI는 제안을 만들고 담당자가 결정한다. 생성 화면만으로 구현 가능성을 확정하지 않는다.

## 7. 데이터가 쌓이는 구조

Request → 요구사항 버전 → 분석 실행 → 자원·근거 → 협의·수용 기준 → 산정·리포트 → 등록 스냅샷 → 실제 수행 결과 → 검증 완료 Case.

근거에는 출처 식별자, 자원 경로, 기준 버전, 관찰 사실과 추론의 구분을 포함한다. 사례에는 유사 이유와 다른 조건을 모두 표시한다. 실제 공수가 없는 사례를 실제 실적처럼 비교하지 않는다. ‘경험 축적’은 우선 검색 가능한 구조화 저장을 뜻하며 모델 자동 재학습을 전제하지 않는다.

운영 단계에서는 조직·프로젝트별 접근 범위, 보존 기간, 삭제·비식별 정책을 정한다. AI 외부 전송 여부와 사용 가능한 원천 자료 범위를 도입 조직과 합의한다.

## 8. 성과지표와 검증 방법

아래 수치는 과제 정의서의 목표이며 아직 측정된 효과가 아니다. 파일럿 이전 동일 업무군의 기준값을 수집한다.

| 지표 | 측정 정의 | 목표 | 측정 시 주의점 |
|---|---|---|---|
| 요구사항 확정 소요시간 | 접수~확정 경과시간, 실제 작업시간 별도 | 기준 대비 50% 단축 | 현업 응답 대기시간 분리 |
| 개발 중 요구사항 변경 | 해석 차이·누락으로 변경된 건 / 개발 착수 건 | 변경률 50% 감소 | 신규 사업 요구 변경 별도 |
| 영향도 분석 시간 | 분석 착수~담당자 확인의 작업시간 | 50% 단축 | 시스템·복잡도별 비교 |
| 공수 예측 오차 | Σ|예상-실제 공수| / Σ실제 공수 | 기준 오차 대비 30% 개선 | 실제 합계 0이면 산출 제외 |
| 완료 Case 구조화율 | 필수 실제 결과가 검증된 Case / 완료 대상 건 | 100% | 검토 등록 건수로 대체 금지 |
| 사례 활용률 | 추천 사례를 근거로 채택한 요청 / 추천 제공 요청 | 파일럿 후 설정 | 자동 추천 표시와 채택 구분 |

오차 30% 개선은 상대 개선이다. 기준 오차 40%라면 목표는 28%다. 측정 기간·표본 수·복잡도 분류를 함께 공개한다. 해커톤에서는 실제 생산성 효과 대신 흐름 완주, 근거 추적, 버전 변경 후 등록 차단을 검증한다.

## 9. 도입·경제성 설계

1. 한 시스템의 대표 SR과 비식별 과거 사례를 선정한다.
2. 기존 방식과 보조 도구 사용 방식을 비교하고 담당자 확인 결과를 수집한다.
3. 요구사항 합의와 검토 이력부터 도입한다.
4. 레거시 검색·실제 산정·실적 환류를 순차 연결한다.

내부 업무 개선을 1차 모델로 둔다. 외부 판매는 검증 후 조직/워크스페이스 구독 또는 사내 구축형을 검토한다. 가격과 시장 규모는 자료가 없어 확정하지 않는다.

월 순효과 = 월 처리 건수 × 건당 절감 작업시간 × 내부 시간당 비용 − 월 운영비 − 월 환산 도입비.
운영비에는 모델 호출·색인·저장·보안·자료 정비·검토 비용을 포함한다. 회의 대기시간을 모두 인건비 절감으로 계산하지 않는다. 재작업 감소와 분석시간 감소를 중복 합산하지 않는다.

## 10. 주요 위험과 대응

| 위험 | 대응 |
|---|---|
| 분석 누락·생성 오류 | 근거 표시, 사람 검토, 미확정 조건 관리 |
| 오래된 시스템 정보 | 기준 버전·분석일 표시, 변경 시 재분석 |
| 부정확한 과거 사례 | 실제값 여부·조건 차이·출처 표시 |
| 민감정보·악성 HTML | 시연은 비식별 샘플, 격리 미리보기, 운영 접근 통제 |
| 현업 입력 부담 | 텍스트·HTML 경로 제공, 수정 가능한 초안 |
| 과도한 자동화 기대 | 화면·다운로드에 mock 표시, 승인 책임 명시 |

## 11. 의사결정이 필요한 항목

확정 주체와 승인 정책, 리포트 최종 양식, 1일 기준시간과 MD 정의, 휴일·인력·병렬 작업 규칙, 레거시 연결 범위, 실제 실적 자료 확보, 보존·접근 정책은 미확정이다. 팀 현황과 MD 다운로드의 MVP 포함 여부도 구현 착수 전에 확인한다.

해커톤 완료 기준은 대표 요청에서 입력→분석 후보 확인→적용 Mock→협의 확정→리포트 등록→이력 조회가 끊김 없이 이어지고, 수정 시 이전 결과 등록을 차단하며, mock을 실제 분석으로 오인하지 않게 표시하는 것이다.
